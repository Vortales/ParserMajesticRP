# ultiparser 1.16 — разбор алгоритма

Анализ полного цикла парсера: откуда берутся данные, как страницы скачиваются
и во что превращаются. Основано на коде `ultiparser1.16.py` и реальных файлах
прогонов (`ultiparser1.14/forum.majestic-rp.ru/Результаты/`, 128 docx).

## 1. Общий конвейер (не менялся с 1.14)

```
🔑 Войти  →  🔍 Сканировать (Этап 1: дерево разделов/тем)
       →  пометки «Общие правила»/«Сервер» + чекбоксы тем
       →  Этап 2 (глубокий парсинг тем: посты, даты, картинки/OCR)
       →  🚀 Сформировать документы (docx-базы знаний)
```

Состояние между запусками: `forum.majestic-rp.ru/structure.json` (дерево),
`checks.json` (галочки/пометки), `cookies.json`, `thread_dates.json`,
`_cache/` (сырые страницы/темы), `images/`, файл промта (`promt 1.5.txt`).

Рабочий цикл генерации: для общих тем и тем каждого сервера
`threads_to_lines()` превращает закэшированные темы в строки
(с учётом фильтров, аббревиатур, telegraph-замен, OCR),
затем `build_common_docx()` / `build_server_docx()` собирают документы.

## 2. Формат результатов (сохранён один в один)

```
Результаты/
└── Общие правила/
    ├── Общие правила.docx              # слой 2 (общие) + слой 1 (промт внизу)
    ├── Темы/                           # отчёты Этапа 2 по общим темам
    │   └── <Название темы>.docx        # «ПЕРВЫЙ ПАРСИНГ» / diff изменений
    └── <Сервер>/                       # напр. «Majestic РП Memphis»
        ├── <Сервер>.docx               # слой 2 + слой 3 (база сервера) + промт
        └── Темы/
            └── <Название темы>.docx
```

Слои внутри серверного документа (сверху вниз):

```
2. ОБЩИЕ ПРАВИЛА (правила проекта)
   ════════════════════════════════════════════════════════════
3. ЗАКОНОДАТЕЛЬНАЯ БАЗА: <сервер>
   ════════════════════════════════════════════════════════════
1. ПРОМТ  ← самый низ, чтобы ИИ точно держала его в памяти
```

Хвостового шаблона `«В конце ответа всегда пиши ===КОНЕЦ ОТВЕТА=== ...»` нет
ни в одном документе (удалён ещё в 1.15 — требование уже есть в самом промте).
Типографика единая (`DocxGen`: Times New Roman, межстрочный 1.0, поля 0.4),
каждый топик-отчёт начинается с заголовка, URL, даты и блока изменений.

## 3. Гибридный транспорт 1.16 (новое)

Раньше каждая страница скачивалась через Selenium-браузер: надёжно, но медленно
(3,5–7 с паузы на страницу + вес браузера). В 1.16 добавлен быстрый путь —
прямые HTTP-запросы через `requests` с cookies авторизации, как у разработчика,
парсившего «напрямую по кукам». Браузерный движок 1.15 сохранён целиком
и теперь работает фолбэком.

```
                    ┌─────────────────────────────┐
                    │  HttpClient.get(url)        │
                    └──────────────┬──────────────┘
                                   ▼
                    ┌─────────────────────────────┐
           ┌─────── │ fast пригоден?              │ ───────┐
           │       │ (чекбокс ⚡ + есть cookies + │        │
           │       │  не в окне «только браузер») │        │
           │       └─────────────────────────────┘        │
           ▼                                              ▼
┌─────────────────────────┐                    ┌─────────────────────┐
│ БЫСТРЫЙ ПУТЬ (2 попытки)│                    │ БРАУЗЕР (до 5 попыток│
│ · лимитер: слот ≥1,2с   │   ┌─────────────── │  + DDOS-пережидание)│
│ · пауза 1,2–2,8 с       │   │ фолбэк        │ · ленивый старт     │
│ · таймаут 25 с          │───┘ при отказе    │ · сбор свежих cookies│
│ · проверка ответа (п.4) │                   └─────────────────────┘
└─────────────────────────┘
```

Быстрая сессия (`requests.Session` на поток, keep-alive):
cookies синхронизируются по счётчику ревизий (браузерный сбор освежает их
без перезапуска), заголовки — браузерные: UA из версии реального Chrome,
`Accept-Language: ru-RU`, `Sec-Fetch-*`, `Referer` форума.

## 4. Проверка быстрого ответа (точность вместо скорости)

Быстрый ответ принимается, только если **все** условия выполнены:

1. HTTP 200 (403/429/5xx → сразу в браузер, без повторных попыток);
2. финальный URL — не `/login` (редирект на вход = слетевшие cookies);
3. в HTML нет формы входа (`login`+`password`+`/login/login`);
4. `html_ok`: нет антибот-маркеров («just a moment», «checking your browser»…);
5. не «подозрительная тема»: URL вида `/threads/`, но в HTML нет ни постовых
   маркеров (`message--post`, `bbWrapper`…), ни маркеров штатной ошибки
   («no permission», «not found»…) — такая страница перепроверяется браузером,
   а не молча принимается. Штатные страницы ошибок (нет прав / нет темы)
   принимаются как есть — это корректный результат, а не блок.

Каждое нарушение + сетевой сбой = «блокировка» для статистики.

## 5. Антибот-защита (почему не будет бана за скорость)

- **Глобальный лимитер** один на все потоки: старты запросов разнесены
  минимум на 1,2 с + джиттер; слот занимается под мьютексом до паузы —
  параллельные потоки физически не могут выстрелить пачкой.
- **Адаптивный бэк-офф**: каждая неудача замедляет лимитер (до ×4),
  успехи плавно возвращают темп.
- **Режим «только браузер»**: 3 блокировки подряд → быстрый путь
  отключается на 5 минут, всё идёт через браузер; успешный сбор свежих
  cookies сокращает окно до 60 секунд.
- **Ленивый браузер**: пока быстрый путь справляется, Selenium может
  вообще не стартовать; повторные попытки старта — не чаще раза в минуту.
- Паузы перед запросами сохранены и в браузере (3,5–7 с), и в скачивании
  картинок; «Потоки» выше 4 и частые «🔑 Войти» по-прежнему запрещены
  здравым смыслом — это главный триггер детекта (~10 минут блока).

## 6. Что ещё ускорено/исправлено точечно

- `thread_dates.json` читается из памяти с защитой по mtime файла
  (запись через `save_thread_dates` обновляет кэш) — вместо чтения
  с диска на каждую тему.
- Дата создания темы: regex по первым 200 КБ HTML вместо полного
  BeautifulSoup-парсинга каждой страницы; контракт тот же (паритет проверен).
- Пауза между заголовками тем в браузере использует быстрые задержки,
  когда включён fast.
- Картинки с хоста форума сначала пробует быстрая сессия —
  до прокси/браузера.
- `done` считается и на пропущенных темах (битые ссылки, готовое из кэша) —
  прогресс доходит до 100%.
- Слияние деревьев по якорному ключу: якорные категории (`/#...`)
  больше не обмениваются пометками «Общие/Сервер» друг с друга.
