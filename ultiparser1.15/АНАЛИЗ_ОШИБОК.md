# Анализ кода ultiparser (v1.14 → v1.15)

Дата: 2026-09-29. Номера строк ниже — по файлу `ultiparser1.14.py` (6806 строк).

**Главная оговорка:** код полностью рабочий и соответствует заданной логике.
Ниже — не список багов, а разбор «точек внимания»: что проверено и хорошо,
где есть мёртвый код, мелкие несогласованности и поведение, о котором стоит знать.
Исправлять ничего из этого **не обязательно** — в версии 1.15 логика не менялась,
кроме порядка слоёв в документе (см. раздел 6 и `README.md`).

---

## 0. Что проверено и хорошо (сильные стороны кода)

- **Потокобезопасность GUI.** Фоновые потоки не трогают tkinter напрямую:
  `RichLog.log` идёт через `after(0, ...)` (строка 3589), диспетчер процессов
  опрашивает очередь через `after(50, ...)` (`_poll`, строка 3766),
  перестроение дерева/отчёты — через `after(0, ...)`. Очередь `ProcessEmitter.q`
  потокобезопасна по построению.
- **Один браузер — строгая очередь.** `_browser_fetch` (строка 5547) держит
  `_fetch_browser_lock` на всё время запроса (навигация + ожидание). Это correctly
  закрывает классическую гонку Selenium-вкладки при параллельном сканировании
  (в коде есть подробный комментарий).
- **Защита состояния.** `save_struct` отказывается сохранять пустую структуру (не даст
  затереть `structure.json` провальным сканом); Этап 1/Этап 2 делают снимок состояния
  «до», а после показывают отчёт об изменениях чекбоксов/пометок.
- **Восстановление выбора переживает пересканы.** `checks.json` + `_restore_checks`
  (точные URL) + `_apply_pre_scan_selection` с anchor-aware ключом `node_key`
  (якоря `/#...` не ломаются нормализацией). Автоотметка новых разделов/тем по
  ключевым словам + фильтр по дате (`evaluate_thread_keyword_match`, строка 3447).
- **Контрольная сумма по контенту.** Живой путь сверки тем — `compute_content_checksum`
  по постам/блокам, а не по сырому HTML (не зависит от счётчиков, рекламы, времени
  визита). Построчный diff — `diff_thread_blocks`.
- **Картинки и OCR.** Кэш скачанных изображений и OCR-текста по `sha256(url)`,
  лимиты размера/количества, каскад методов скачивания (прямой → прокси форума →
  вкладка браузера), пропуск смайликов/иконок, извлечение реального URL из
  `data-url`/`proxy.php?image=`. Рекурсия не теряет картинки внутри `<p>`,
  цитат и спойлеров даже при `skip_text=True`.
- **Парсинг UIX-темы.** `find_subforums` корректно обрабатывает главную
  (`uix_categoryTitle` → категории + подразделы) и страницы разделов, есть
  диагностика и аварийный fallback.
- **Промт с BOM читается.** `_load_prompt_text`: сначала `utf-8-sig`, затем `cp1251`.
  Файл `promt 1.5.txt` как раз с BOM — учтено.
- **Дедупликация.** `norm_thread_url` схлопывает `/post-NNN`, `/unread`, query/fragment;
  серверные папки при коллизии имён расходятся через md5-суффикс (`_server_dir_names`).
- **Нормализация для совпадений.** `normalize_title_for_match` (нижний регистр,
  `ё→е`, без пунктуации) + `evaluate_thread_keyword_match` с fail-open при
  отсутствующих/битых датах (тема включается, а не теряется).

## 1. Латентное (единственное значимое): коллизия якорей в `merge_preserve_state`

- **Где:** `norm_url` (строка 968), `_index_nodes_by_url` (1738), `merge_preserve_state` (1750).
- **Суть:** `norm_url("/#majestic-rp-memphis.1462")` отрезает всё после `#` и даёт `"/"` —
  **одинаковый ключ для всех корневых категорий-якорей**. В индексе `old_idx` они
  перезаписывают друг друга (выживает последний), и при слиянии после Этапа 1
  каждая новая якорная категория получает `mark`/`thread_checks`/`threads`
  одного и того же (произвольного) старого якоря.
- **Почему это не ломает работу:** пометки «Сервер» живут именно на якорях (уровень 0),
  но сразу после слияния Этап 1 вызывает `_restore_checks`, который восстанавливает
  пометки/галочки по **точным** URL из `checks.json`, — сбой маскируется.
  А `structure.json` на диске самолечится при следующем сохранении из памяти.
- **Когда может проявиться:** только если `checks.json` удалён/устарел, а структура
  пересканирована — тогда пометки «Сервер»/«Общие» на корнях могут перепутаться.
- **Рекомендация (опционально):** в `merge_preserve_state` использовать тот же
  anchor-aware `node_key`, что уже есть в `_apply_pre_scan_selection`, и вынести
  его в общий хелпер, чтобы ключи слияния не расходились в двух местах.

## 2. Мелочь (косметика): прогресс недотягивает до total при ошибках парсинга

- **Где:** `App._do_generate` → `work()` (ветки «не удалось загрузить» и «битая ссылка»).
- **Суть:** обе ветки делают `return` **без** `done[0] += 1` (в отличие от ветки
  пропуска по дате, где инкремент есть). При failed-темах счётчик `d/total`,
  статусбар и прогресс-бар останавливаются вида `48/50`.
- **Влияние:** только отображение; на документы и отчёт `failed_threads` не влияет.

## 4. Несогласованности и поведение, о котором стоит знать (не баги)

1. **Два каталога логов:** файловый логгер пишет в `logs/` (строка 173),
   а `chrome_debug.log` — в `_logs/` (строка 643). Оба создаются автоматически.
2. **`DocxGen.add("")` — no-op.** Все вызовы `g.add()` без текста ничего не вставляют,
   поэтому пустых абзацев в docx нет — плотность текста максимальная, разделители
   только строкой `===...`. Судя по всему, так и задумано (компактность для ИИ).
   Следствие: `_collapse_paragraphs`/`_remove_rsid_attrs` при текущем `add()`
   фактически нечего делать — безвредно.
3. **`_save_topic_docx` не применяет фильтры.** Потемные docx всегда содержат полный
   сырой текст (без `topic_filters`/`abbreviations`/`telegraph`), тогда как сводные
   документы — с фильтрами. Похоже на задуманное (полный архив темы), но стоит знать.
4. **Подпись «контрольная сумма отличается» при первом парсинге.** Для новых тем
   (`diff_lines=None`, метка «ПЕРВЫЙ ПАРСИНГ») в файл пишется строка
   «(контрольная сумма отличается, построчный diff не найден)» — для первого
   парсинга формулировка сбивает с толку. Косметика.
5. **Пустой OCR кэшируется навсегда.** Если движка не было и распознавание дало `""`,
   пустой `.txt` в `images/` означает «больше не пытаться». После установки
   EasyOCR/tesseract для ретрая нужно удалить соответствующие `.txt`.
   (На CPU-машине `EasyOCR(gpu=True)` сам переключается на CPU с варнингом;
   `pytesseract` требует внешний бинарник tesseract.)
6. **`prompt_path` абсолютный.** Ломается при переименовании/переносе папки
   (ровно это и произошло при переименовании `ServerParser` → `ultiparser1.14` —
   исправлено в конфиге и чинится скриптом `migrate_data.py`). В идеале хранить
   относительный путь; как минимум — помнить, что после переезда папки промт
   нужно выбрать заново кнопкой «📄 Выбрать».
7. **Ключевые слова разделов действуют и на темы.** В `_apply_pre_scan_selection`
   и `scan_deep` темы проверяются не только по `should_autocheck_new_thread`,
   но и по `should_autocheck_new_node` (список разделов). Похоже на осознанный выбор.
8. **`_propagate_thread_selection` только ставит галочки** (не снимает) — by design,
   в коде так и написано. Консистентно с `_collect_checked_threads`, который смотрит
   только на чекбоксы тем, а не разделов.
9. **Даты тем:** `extract_thread_creation_date` берёт **первый** `time.u-dt` на странице
   (предположение: это дата создания темы — для первой страницы темы верно).
   `evaluate_thread_keyword_match` при непарсящейся дате включает тему (fail-open).
10. **Тайминги антибота (by design):** `_wait` ждёт до ~3 минут + ещё столько же после
    reload; `_fetch_soup` — до 5 попыток с растущими паузами; `HttpClient` без
    браузера возвращает `None` («режим только браузер»). Сканирование медленное,
    но предсказуемое.
11. **`IMAGE_LOCK_WAIT=3с`:** если браузер занят дольше — методы скачивания картинок
    через вкладку пропускаются для этого изображения (только для него).
12. **Зачекиненные `Результаты/` собраны по старой раскладке** (сервер внутри
    «Общие правила/»), а текущий код пишет серверы в `Результаты/Серверы/`.
    При регенерации появится новая раскладка, старые файлы затронуты не будут.
13. **`_ensure` возвращает `None`** (falsy) при неустановке опционального пакета —
    для флагов `HAS_*` это корректно.
14. **`_check_all`/`_uncheck_all` с `recursive=False`** всё равно синхронизируют темы
    самого узла (цикл по `THR::` внутри `_set_check`) — поведение корректное.

## 5. Что НЕ является проблемой (частые ложные срабатывания при ревью)

- Длинные `sleep`/повторы — осознанная защита от антибота, а не «тормоза».
- `MAX_WORKERS=1` и комментарий «потоки не ускоряют сканирование» — правда:
  браузер один, запросы строго последовательны (`_fetch_browser_lock`).
- `PERSISTENT_PROFILE`/`DRV_CACHE` используются функциями, объявленными выше их
  определения в файле, — это нормально: вызовы происходят после импорта модуля.
- `_nmap` смешивает ключи iid и URL — так задумано (`iid == url` для первых вхождений).
- Общие документы создаются даже при пустом списке тем (если задан промт),
  серверные — всегда по выбранным серверам. Это соответствует логике «промт обязан быть».

## 6. Что изменено в 1.15 (полный список, ничего лишнего)

По `diff ultiparser1.14.py ultiparser1.15/ultiparser1.15.py` (90 строк diff'а, все — ниже):

1. `PARSER_NAME` / `PARSER_VERSION = "1.15"` + версия в консольном баннере
   и заголовке окна (`Форум-Менеджер 1.15`).
2. `SERVERS_ROOT = Path(__file__).resolve().parent` — папка парсера = папка данных
   (вместо `Path("ServerParser")` от текущей директории). Логика путей внутри
   (`Project`, `logs/`, `_cache`, `images`, `Результаты`) не менялась.
3. `build_server_docx`: порядок `ПРОМТ → ОБЩИЕ → БАЗА → хвост` заменён на
   `ОБЩИЕ → БАЗА → ПРОМТ` (промт в самом низу); строка-хвост удалена.
4. `build_common_docx`: порядок `ПРОМТ → ОБЩИЕ → хвост` заменён на
   `ОБЩИЕ → ПРОМТ` (промт в самом низу); строка-хвост удалена.
5. В `ultiparser1.14.py` изменена **ровно 1 строка**: `SERVERS_ROOT` теперь указывает
   на переименованную папку `ultiparser1.14` (иначе старая версия после переименования
   создала бы `ServerParser` заново). Логика 1.14 не тронута.

Удаление хвоста безопасно: требование писать маркер конца ответа уже есть
в самом промте (`promt 1.5.txt`: «В конце ответа всегда пиши ===КОНЕЦ ОТВЕТА=== ...»),
а теперь промт идёт последним, и модель гарантированно его видит.

- Прогон извлечённых `build_server_docx`/`build_common_docx` со стабом `DocxGen`:
  порядок абзацев `ОБЩИЕ → БАЗА → ПРОМТ(last)`, хвоста нет, пустой промт

- `migrate_data.py` прогнан на копии данных: файлы состояния и промт скопированы,
  `prompt_path` в конфиге переписан на новую папку.
